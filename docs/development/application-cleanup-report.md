# Application folder cleanup report

Completed phase 2's application folder; runtime and composition are subsequent folders. Related changes outside application repair metadata ownership, UI test imports and entrypoint wiring.

## What was there and what it does

The original folder contained 15 Python modules, 5,368 lines and 180 class/function definitions (including methods). It coordinated runtime startup, conversation processing, emotion/reflection, ACT delivery, fleet notifications, memory review and reviewed evolution/release operations.

Production paths traced:

- `sofia.__main__` → `SofiaApplication` → composed runtime and conversation service → `start/respond/stop`; terminal `ConversationLoop` is owned by `sofia.ui.terminal`.
- Desktop/tray → UI controller/worker → application lifecycle and conversation. Dynamic UI lookups use `chat_storage_mode`, `chat_state_path`, `latest_matrix_trace` and `open_channel_conversation`; these remain supported.
- Discord live adapter → application conversation/channel services → scoped conversation processing.
- Bootstrap → emotional conversation → base conversation → matrix planning/execution, persisted assistant responses and proposed-memory learning coordinator.
- Bootstrap startup → background registration factory → coordinator → bounded reflection, ACT, fleet, habits, presentation and heartbeat callbacks. Shutdown/rollback belongs to bootstrap.
- Bootstrap → ACT sender configuration and fleet notice factories. Explicit delivery authorization, recipient/channel/destination restrictions and existing durable stores remain enforced.
- Application exposes authenticated memory review and reviewed evolution/release services. Host runtime also uses the release factory.

## What was wrong, merged and deleted

ACT sender configuration was separated from its service while four fleet factories repeated notification destination validation. The wiring now lives with the ACT service and those factories call one validator. Merely configuring a destination does not enable delivery.

Runtime duplicated package metadata logic; release tooling imported the application layer for metadata. Both now use `sofia.package_metadata`, also exposed lazily through the existing public application exports. The old application metadata and ACT wiring files are deleted without compatibility shims.

Removed uncalled `SofiaActService.bind_message` (a duplicate outbox binding wrapper), the redundant `local_state_path` property, the uncalled `conversation_learning` property and an accidental private matrix-helper re-export. Production learning remains wired internally. Removed four unused matrix imports.

## What was split, moved and fixed

About 300 lines of background task registration moved from bootstrap to `background_runtime.py`. Bootstrap remains the lifecycle owner; registration creates callbacks without starting threads. Both background and model lifecycle workers are now owned before `start()` so rollback stops workers that fail partway through startup. Two regression tests verify this behavior and conversation closure ordering.

One matrix reset routine now clears derived turn state at construction, each new turn and fail-closed recovery. One response persistence routine now saves/reloads the assistant response for ordinary, clothing and awareness responses, preserving awareness consumption after durable save.

All application public exports are lazy. Fresh-process tests exercise both import orders, runtime-first imports and metadata-first imports, including a check that package/metadata imports do not eagerly initialize runtime/conversation/bootstrap.

Stale tests now import the canonical terminal loop and matrix helper. The default desktop entrypoint test supplies a mocked production configuration and verifies that the same object reaches tray and desktop. UI storage tests use the canonical chat path. These repairs remove four pre-existing failures from the full-suite baseline.

## Canonical ownership and what remains

`SofiaApplication` owns its configured runtime, channels and lifecycle handles. Conversation services own scoped sessions over the configured durable store. Matrix context is derived turn state, reset in one place. Background scheduling owns its thread and budgets; its registration factory does not own another runtime. Package name/version have one shared implementation.

Public diagnostic and explicit operator APIs are retained deliberately, even when their named callers are tests: evolution apply/rollback, memory review/promotion, event clarification and expression-plan diagnostics are authority or inspection boundaries. No current live UI caller is claimed for those operator methods. Test coverage alone was not the reason to keep them. Dynamic getters and callback registration are counted separately from lexical references. Future frontend wiring is outside this folder's scope.

Conversation/emotional/matrix modules remain substantial because they coordinate one processing responsibility; deeper cognition/conversation and state-model consolidation belongs to later phases. Runtime received only the related metadata repair. No live Ollama inference, Discord connection or desktop rendering was verified.
