# PKG-INTERACT: on-screen avatar and screen-interaction contract

**Status:** implementation planning, not a deployed feature. **Decision:** after the current PKG-CORE pytest/regression and brief live-acceptance checkpoint, PKG-INTERACT is the next feature package; PKG-MEM follows it. SAFE and VERIFY prerequisites apply throughout. This specification refines [the INTERACT and CLEAN contracts](package-clean-interact-lab-contracts.md) and is the authoritative clarification of the previously provisional avatar/lab scope. The avatar's renderer and visual design can be selected later without blocking the headless event, policy, reaction and lab work. No production code or deployment is authorized merely by this document.

## What Sparks requested

1. **Sofía interacting through her own avatar:** when an avatar is actually displayed, Sofía can intentionally change its pose, gaze, fox-ear/tail expression and other supported representational gestures. She can represent self-directed interactions with her own mapped avatar regions (for example, adjusting an ear or tail or clothing) when the renderer supports them. The avatar is an interface to one Sofía, not a second autonomous character or physical body; no model-generated movement is a claim that actual skin, nerves or hardware felt contact.
2. **Sparks interacting with Sofía's avatar:** pointer clicks/taps and, where supported, drag/hold/gesture input directed at *any* canonical avatar region generate typed events with accurate hit-testing, including head, ears, tail, limbs and private/intimate regions, which remain subject to explicit appropriate adult-only opt-in, the applicable product/session policy and current boundaries. Never silently map a blocked area to a permitted area. A click is not automatically a pat or a particular emotional reaction: duration, gesture and context matter, and unknown properties stay unknown.
3. **Sofía interacting with what is on screen:** with an explicitly enabled and scoped screen/desktop capability, Sofía may perceive authorized screen content, distinguish her own avatar window from other applications, and propose or perform specific authorized UI operations through a trusted executor. A screen observation is not itself approval to click, type, capture microphone/camera, control a game, or modify a file. No ambient capture by default; disclose the active window/target, user-visible listening/observation state, permission, actual result and failures.
4. **Lab:** the initial lab is an isolated virtual scene and interaction test harness, not an actual room, homelab or robot. It can simulate screen objects, avatar hit regions, gestures, policy decisions, emotional responses and supported animations without touching production conversations, memories, grants or external devices. A future physical or game-engine lab requires an explicitly identified adapter and separate authority and hardware gates.

## Logical boundaries and interfaces (adapt to inspected code, do not create duplicate owners)

`Trusted input (pointer/text/lab/authorized sensor) -> authenticated actor and session -> target selection (avatar region versus external screen object) -> canonical hit-test/intent resolution -> SAFE consent and capability gate -> contextual reaction or scoped UI action proposal -> UI renderer/tool executor -> observed result and evidence-linked journal -> optional reviewed MEM promotion`.

**Avatar input event:** stable event/session/client/actor IDs, timestamp, source modality, avatar revision/pose/viewport transform, target kind=`avatar`, canonical region ID plus side/subregion, coordinates in canonical local space when known, gesture phase (`begin`, `update`, `end`, `cancel`), verb classified only when justified (`tap`, `pat`, `stroke`, `drag`, `hold`, `withdraw`, `unknown`), user-supplied duration/pressure only when actually available, provenance, policy decision and delivery/animation outcome. A pointer event outside the avatar, over an occluded region or against a stale renderer revision must be an explicit miss/unknown, not a guessed body part. Do not retain raw precise coordinates or private interaction logs longer than the approved policy permits.

**Avatar self-action:** distinct actor=`sofia`, intent and supported animation/region IDs, reason/context, actual renderer acknowledgment, cancellation and expiry. The LLM may suggest expressive movements but cannot invent a renderer acknowledgment, override blocked regions, operate other apps or initiate physical touch. Self-directed avatar gestures do not count as user consent to reciprocal interaction.

**External-screen observation/action:** target kind=`screen_object`, exact user-authorized app/window/session, freshness and provenance for observation, bounded requested operation and grant scope, independent executor outcome and revocation. Separate read-only observation from pointer/keyboard/file/network authority. A mouse click intended for the avatar never falls through into another application; overlay passthrough and focus must be tested explicitly.

**Region model:** validate a versioned canonical all-region hierarchy against the actual avatar representation; support mirroring, pose changes, scaling, overlapping geometry, transparent pixels, occlusion and inaccessible/offscreen regions. The region map includes private/intimate areas for explicit restricted-policy handling rather than omitting anatomy. No arbitrary LLM string or pixel coordinate can bypass restricted-region policy. Resolve ambiguous overlapping targets with deterministic priority or visible clarification, and do not convert an avatar-region ID into a Gaia actuator ID.

**Reaction:** derive `accept`, `decline`, `clarify` or `acknowledge` from policy, current scene/task, context, relationship evidence and reviewed preferences; then offer a contextual modeled emotional blend to existing `EmotionalJournal`/expression guidance, and only render an actual supported response. A missed click, denied contact or unacknowledged animation must not be recorded as an accepted touch. No forced enjoyment, automatic escalation, repetitive mandatory gestures or claims of real sensory experience. A serious conversation remains answer-first; user stop and change of topic are honored promptly.

**Consent/privacy:** normal social touch and self-expression are distinct from restricted intimate/private-region interaction. Restricted mode defaults off; it requires explicit appropriate adult-only opt-in and currently valid session/actor/region policy, is revocable without delay, and does not cross devices, clients, lab/production, or virtual/physical contexts. User initiation is not blanket consent. The persona can depict a boundary or refusal. Do not infer age, consent or arousal from anatomy, clothing, emotion or prior head pats. No background screen recording, private image storage or automatic promotion of intimate interactions into durable relationship memory. An immediate stop cancels animations and pending virtual actions at the controlling UI boundary, with independently controlled stops for any future physical device.

## First delivery and later visual integration

**INTERACT first, without a finished animated avatar:** audit current canonical embodiment and emotional journal; implement/design a typed interaction boundary, versioned region mapping, explicit consent and policy evaluation, self-action contract, simulation scenes and source-linked reaction adapter. Use a test renderer or hit-test fixture to prove coordinate translation and policy; do not label this a shipped on-screen avatar. UI owns eventual rendering, pointer/touch transport, visual design, animation, multi-client session and optional voice synchronization. On-screen appearance is not a prerequisite for INTERACT's *headless* acceptance, but actual clicking and self-directed movement are separately marked **not run** until a real renderer exists. MEM comes next and can enrich long-term preferences only from reviewed source-linked evidence. SAFE/VERIFY run concurrently; NET/BODY do not gain permissions through this package.

**Acceptance matrix:** A1 canonical region coverage including restricted regions and honest unknown/miss; A2 click/tap/hold/drag/cancel coordinate tests across pose, scaling, mirror, overlap and occlusion; A3 trusted actor, opt-in, denial, stale consent, replay and stop enforced outside the LLM; A4 self-action request/renderer acknowledgment versus rejected or unsupported animation; A5 explicit avatar click isolation from underlying desktop; A6 screen read-only versus actionable grant, visible scoped capture and real executor result; A7 source-linked context-sensitive reactions in serious/playful/neutral/boundary cases with real model review when available; A8 lab reset/replay preserves production state and cannot access live screen/homelab/network/robot; A9 crash/reconnect/restart do not double-apply gestures or invent sensations; A10 real rendered end-to-end touch/self-animation and any actual screen action each require separately recorded live evidence. Every line records pass/fail/not run and fixture versus actual hardware/client.

**Open implementation selections:** inspect canonical anatomy and authority clauses; choose renderer, hit-test coordinate system and overlay focus behavior; decide allowed external desktop applications and capture retention, exact restricted-mode UX/privacy defaults and whether any lab extends beyond simulation. Record chosen values before implementing their dependent capabilities. The specification sets behavior and test gates, not fabricated current Python APIs, established consent state or a claim of installed screen-control tooling.
