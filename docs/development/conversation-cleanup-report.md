# Phase 3: conversation cleanup

## What was there / what it does

Three modules, 303 lines: a package marker, the persisted session/message/role contracts, and one SQLite conversation store. Production application/bootstrap/channel construction creates stores at the canonical configured state path. Conversation services create/load sessions and save/list messages; UI local and remote clients project those same models; habits and reviewed-memory learning consume persisted messages. Store open/close is part of application lifecycle, not a test-only API.

## Every file: classification

| File | Decision | Responsibility |
|---|---|---|
| `__init__.py` | KEEP | Empty package marker; no compatibility export needed. |
| `model.py` | KEEP | Immutable persisted session/message values and two transcript roles. |
| `store.py` | KEEP / FIX | One durable transcript owner, with atomic writes and resource recovery. |

The small model and store remain separate: provider CognitiveRole includes system/tool roles and does not replace the user/assistant persisted transcript contract. No duplicate production session model or unused class/function was found in this folder. No files were merged, deleted, renamed or moved.

## What was wrong / what was fixed

A message save inserted its row before updating session activity. If the second statement failed, the connection retained the uncommitted message, and a later commit could persist it. The message and activity update now share one connection transaction, which commits the complete operation or rolls it back. Session creation uses the same transaction boundary.

Store opening assigned the live connection before schema initialization. A failure left that connection open, and subsequent open calls treated initialization as complete. Initialization failure now closes and clears the handle before propagating the failure, allowing clean reopen.

Two regressions reproduced both defects before changes. The first installs a SQLite trigger that aborts session activity updating and verifies no message or session change survives. The second forces initialization failure, verifies the store remains closed, then verifies successful reopen/session persistence. Both exercise observable storage behavior rather than internal-only implementation details.

## Dependency repairs / canonical state / what remains

Existing production imports and signatures remain correct, so no related outside-folder source change was needed. One configured database path, one lock and one live connection remain the storage authority. Persisted session/message classes carry values, not duplicate active ownership. No schema, authority or privacy policy was changed. The package stays compact; further transcript privacy/history selection belongs to application and social boundaries already wired above it.
