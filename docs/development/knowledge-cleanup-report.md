# Phase 6: knowledge cleanup

## What was there / what it does

Twelve modules implement provenance-backed source documents/facts, freshness, audience policy, ingestion/retrieval, and capability bindings. The original symbol/import/reference inventory is appended.

Production chain: composition -> SQLiteKnowledgeStore / SQLiteKnowledgeLifecycle / KnowledgeAccessStore -> KnowledgeService -> KnowledgeCapabilitySet -> authorized capability execution. Text/PDF ingestion checks confinement, derives provenance/facts and audience policy; search uses active trusted source facts and audience filtering. Default KNOW matrix routing exposes relevant knowledge capabilities.

## What was wrong / merged / deleted / renamed or moved

JSON writers and standalone ingest prototypes survived beside the production SQLite/service path. Removed the duplicate writers while preserving one-time pure JSON import and collision-free evidence retirement. Merged the small knowledge index beside SQLite persistence. Removed old exports, repaired import/type annotations and converted test setup to canonical SQLite or explicit legacy JSON evidence fixtures.

## What I fixed

Document/fact and lifecycle writes previously changed their in-memory caches before SQLite committed. Failed writes could therefore appear successful to subsequent reads in the same process. Publish cache values only after successful persistence, preserving source registration/conflict validation. New trigger-based failure tests verify the unchanged cached/durable state and successful retries.

Legacy knowledge verification previously compared the entire canonical store with the legacy snapshot, incorrectly rejecting imports when additional canonical documents existed. Verify every imported document/fact without treating extra canonical records as a conflict. Existing matching imports are resumable; conflicting provenance remains rejected rather than overwritten.

## What remains

Provenance, document freshness and audience policy remain separate canonical responsibilities/tables. The KnowledgeStore index is an implementation cache/base used by SQLite, not an independently configured production backend. Service's explicit standalone construction policy remains supported; production supplies the audience store and missing policy fails closed. No production authorizations were broadened. PDF parsing, bounded paths, trusted-source filtering and fact supersession remain covered.
