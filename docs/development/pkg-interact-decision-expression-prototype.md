# PKG-INTERACT: isolated decision -> expression diagnostic

## Evidence driving this prototype

On Windows at `7d9b527`, 15 focused tests passed and the disposable real-app probe finished without the earlier SQLite deletion error. The hug with the extra avatar-scene frame still replied as if *physical contact* was being requested; declining was not itself the defect. The left-ear case supplied dialogue but invented ear sensitivity and unverified earlier interactions. The real-sensor case correctly denied actual physical sensing. These are individual, unseeded model samples, not reliability measurements. The user approved the next isolated architecture investigation, not a production deployment.

## Three boundaries

1. **Interpret:** Reuse reviewed `ActionIntent` or `InteractionDecision` from the existing grammar. No new free-text classifier, new body policy, database writes, or sensor inputs. A real-sensor question is a separate exact synthetic fixture. A denied gesture from the canonical stop gate bypasses both model calls. Recognition is not consent.
2. **Choose:** Send canonical bounded self-state, the reviewed classification and original user text to the configured Ollama model. Require strict JSON with an in-scope `choice` and short diagnostic `reason`. An offer can be accepted, declined, clarified or met with a boundary; a described gesture can be responded to, clarified or met with a boundary. An ambiguous ear only permits clarification. Invalid/malformed responses stop before expression. A choice is *not* a stored preference, consent record, actual contact or animation.
3. **Express:** Send the same canonical context, reviewed classification, exact user text, and only the validated choice. Never insert the model's decision-stage reason into the next prompt as evidence. No emotion-to-gesture mapping, forced affection, executed-action claim, rendered animation or capability authorization. A physical-sensor question bypasses the avatar choice stage and uses verified-capability context instead.

`src/sofia/interaction/decision_expression.py` holds the pure types/request construction/validation. `src/sofia/interaction/decision_expression_probe.py` is an opt-in **state-free** Ollama experiment; unlike the earlier real-app probe it neither constructs `SofiaApplication` nor opens SQLite. `test/test_interaction_decision_expression.py` uses a stub provider, never real inference. This is NOT the exact live session and cannot establish qualitative success from a unit-test pass.

## Review gates

- From the activated venv on `feature/pkg-interact-shared-engine`, run `python -m pytest -q -x test/test_interaction_decision_expression.py` first. Stop on failure. Do not reset or clean the unrelated local changes.
- Only if green, run `python -m sofia.interaction.decision_expression_probe`. Compare the structured choice and its diagnostic reason with the final expression for an offered hug and left-ear pat; confirm that the stopped intrusive gesture never reaches Ollama and the real-sensor question does not use avatar-choice language. An invalid JSON decision is a diagnostic failure, not permission to silently make a default choice.
- **Inspect, do not auto-score**, whether decisions are based on real-world physical impossibility instead of avatar context; whether expression preserves the chosen response without inventing touch, sensations, earlier interactions or performed animation; and whether sensor capability grounding remains accurate. A single acceptable sample is not sufficient. If decision repeatedly defaults to physical impossibility, evaluate a different model or deeper interaction architecture instead of more prose patches.
- Before any live integration: controlled repeated-model review, broader regression suite, CORE/SAFE/privacy/concurrency review, explicit user merge approval. Keep PR #2 draft; no change to `main`, other PRs, live prompts, Constitution, identity, actual emotion journal, state/sofia.db or its backup, unrelated local Ollama test edit, or model settings. Discord, animation renderer and real sensing are not deployed here.
