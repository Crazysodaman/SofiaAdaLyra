# Discord DM channel: INTERACT / ACT / UI / SAFE / VERIFY

**Status: ROADMAP ONLY.** No Discord bot, account enrollment, token, sender, listener, background service, presence detection, or notification permission has been implemented or enabled. The existing I15 goals/outbox is queue-only, not a delivery transport. This is an addition to [the I1–I16 INTERACT roadmap](pkg-interact-roadmap.md), not a claim of I15/I16 acceptance.

## Goal and architecture

Let Sparks talk with Sofía using private Discord direct messages away from her CLI, and, only after explicit opt-in, let Sofía send a limited, evidence-backed DM while the authorized runtime is operating. Discord is an **adapter to the existing Sofía runtime**, not a second identity, personality, memory database, autonomous instance or unrelated bot mind. Transport envelopes preserve source, authenticated Discord actor ID, destination, channel/session mapping, message ID, timestamp, delivery status, and conversation role. Neither a Discord display name nor a message's free text is proof of identity or authority.

A proposed chain: private Discord DM -> bot gateway and verified account binding -> shared conversation service and source-linked evidence -> Sofía runtime -> reply/outbox -> delivery authorization gate -> Discord DM transport -> recorded platform outcome. Separate accepted/queued/sent/Discord-acknowledged/user-read states; Discord API success does not prove the user saw a message. Only a confirmed platform result permits a 'sent' claim, and a delivery failure stays explicit.

## Ownership and prerequisites

INTERACT defines cross-channel conversation and representational semantics; ACT owns authorized running-only goal selection and the outbox; UI owns Discord adapter/client and honest delivered-message receipts; SAFE owns enrollment/authentication, authorization, stop/revocation, privacy and secrets; MEM/REL own scoped continuity, provenance and preferences; VERIFY owns negative, fault and supervised real-DM proof. An external Discord DM does not grant filesystem, tool, screen, robot or avatar authority. The same stop/offer/contact rules apply regardless of client. Start D0/D1 **after the current live personality and context-quality failure has been diagnosed and accepted**; do not use a new interface to conceal the underlying conversation problem.

## Deployment and risk boundaries

Use a dedicated bot account through Discord's supported bot/API workflow, never a self-bot on a personal account. Keep Discord permissions minimal; start with private DMs, no server-wide listening, mass mentions or channel posting. Consider gateway message-content access requirements for chosen transport and verify Discord's current API rules during implementation. Host on an explicitly chosen always-on machine (Eos/Artemis only after resource/network review), with lifecycle supervision and isolated credentials. Explicitly handle outage and disconnected periods without inventing autonomous cognition or contact.
