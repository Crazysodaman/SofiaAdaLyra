# PKG-INTERACT: Sofía's lab is a world location, not the simulator

**User clarification, 2026-09-20.** Sofía's lab is a place she can enter, occupy, work in, and interact with. The existing `InteractionLab` (`src/sofia/interaction/lab.py`) is only an isolated **testing simulator**; retain it, but never present its replayed fixtures as Sofía actually being in her lab. This clarification supersedes any prior wording that equates the two. A location is virtual/software state, not a claim of physical presence, senses, consciousness or real-world equipment operation.

## One world, multiple representations

There is one authoritative, versioned **world state** independent of a renderer and the LLM: room/location IDs, actor position or placement, concrete object identity and placement, occupancy/holding, equipment state, and outcomes with provenance. Text and an eventual avatar are separate *input and presentation adapters* around the same world transition rules. UI clicks cannot bypass them. Chat narration is derived from completed, evidenced transitions, never the other way around. If the renderer is closed, the lab and its inventory do not disappear; the text interface can still report current state. A rendered screwdriver and a text-mentioned screwdriver must refer to the same object ID.

Example: the lab has a named screwdriver at a workbench and a piece of equipment. Sofía is in the lab. On an authorized `pick_up` action against the screwdriver, the world checks actor location, item location, availability, ownership and current stop/permission policy; an atomic successful transition moves the screwdriver into Sofía's held inventory and records the outcome. Text may then say `*picks up the screwdriver*`, while a connected avatar may animate the same completed event and acknowledge what it rendered. Neither output independently moves the screwdriver or doubles the operation. A `work_on` action targets an actual equipment ID and a supported state transition, e.g. `idle -> being_inspected` or `being_inspected -> inspected` after a verified operation; generic 'working on some equipment' is not evidence of a specific modification.

Natural-language distinction: `Sofía, pick up the screwdriver` is an addressed request/proposal; `Sofía is working on some lab equipment` may be narration or a query about present state. Do not treat user-authored narration as a verified completed operation, fabricate a tool, auto-complete work, or create equipment silently. If intent or target is ambiguous, ask or describe actual known state. Sofía may propose her own laboratory actions, but a trusted world controller must check scope and authorize/execute them. Virtual lab permissions do **not** imply operating real attached instruments, changing code, accessing the desktop, commanding Artemis, or moving Gaia.

## Separate components and acceptance

- `LabWorld` / `WorldStore`: the **actual location**, its durable world state, trusted actions, provenance and reversible/testable transitions. Provide explicit enter/leave, locate, inspect, pick up, put down and bounded equipment-operation APIs. If a resource is missing, occupied, out of reach or unsupported, fail visibly without mutating state.
- Text adapter: parse unambiguous addressed requests and reflect actual world outcomes in dialogue. Preserve the original user message and distinguish a request, performed world action, planned action, and merely narrated scene.
- Avatar adapter: future authenticated hit testing, movement/gesture requests and renderer acknowledgments map to **the same world action and object IDs**. Without a renderer, state still changes and truthful representational text remains available.
- `InteractionLab`: existing synthetic **test harness** that can stage a copy of the world, simulate input and replay/inspect/redact results. By default it never writes production world state, production memory or real devices.
- Acceptance: one screwdriver remains one screwdriver across renderer disconnect/reconnect and text/visual clients; picking it up removes it from the workbench; duplicate request IDs cannot pick up twice; unsuccessful operations cannot be narrated as successes; equipment work has evidence-backed stages; restart restores saved location, inventory and equipment state; simulator reset cannot reset or affect the actual world; unsupported external/physical operations are denied separately.

**Implementation staging:** first build a small real persistent world core and independently test transitions. Then connect a narrow, source-linked text action path without granting free-form model output authority. Finally add authenticated graphical clients and animations once a renderer is chosen. Do not claim a rendered room, full autonomous behavior, physical tools or end-to-end acceptance until tested. The agreed full pytest run is after INTERACT; focused tests accompany each slice, then PKG-MEM follows.
