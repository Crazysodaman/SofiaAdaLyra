## How to read this report

- **Type** describes the original work requested: **Design** means design/research deliverable; **Build** means implementation and production integration; **Verify** means evidence-producing tests, benchmarks or actual host acceptance. These are NOT completion levels.
- **Design / coding evidence** is a source-triage classification, not a rigorous code completeness measurement: `Code status unknown` (unassessed), `Partial source/wiring traced`, `Code reported; acceptance unverified`, or design-specific status. Never infer unassessed means unimplemented.
- **Gate 1:** original task requirement satisfied and independently reviewed; **Gate 2:** integrated with production/canonical owners; **Gate 3:** source, security, privacy, recovery/performance audit; **Gate 4:** pinned task-specific unit/integration/regression/platform/installed-wheel proof and independent acceptance. Any original requirement for a real-world/multiday test still needs that test.
- A gate marked **Open** has no recorded gate proof. **Recorded†** means a historical *source packet* exists but is **not independently accepted** and must be rechecked. It does not mean the gate is proven. **Gate 4: Not accepted** is authoritative for all 780 until owner-approved externally authenticated reviewer evidence is provided.
- General final deployment **Gates 5–6 are deferred**, not silently completed. Some originally demanded host trials are prerequisites even at Gate 4.
- **Original requirement / intended outcome** carries the actual task requirement; **Specific remaining proof or action** is a conservative next action grounded in triage and the known source-audit gaps.

## Gate-to-work checklist

1. **Design/research:** compare existing decision artifacts with the original question, complete missing deliverables/tradeoffs, obtain independent/owner review and integrate the approved choice into policy or specification.
2. **Coding:** trace canonical production entrypoint and owner, implement missing source-to-effect behavior including configuration, persistence, consent, principle/audience isolation, idempotency and failure/recovery.
3. **Gate 1:** demonstrate every original requirement is satisfied; acceptance is specific to the task rather than source-file existence.
4. **Gate 2:** demonstrate actual runtime integration and absence of competing databases/authority writers.
5. **Gate 3:** audit evidence provenance, security, resource budgets, OS compatibility, consent, operator stop, restart and negative cases.
6. **Gate 4:** run pinned CI and task-specific relevant selectors, installed-wheel tests, Windows/Linux and any explicitly required host/soak trials. Obtain independently authenticated signed acceptance. Preserve all original trial evidence.
